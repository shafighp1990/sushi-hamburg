PAYMENTS
Checkout opens only after at least one real staff account has been provisioned. This prevents public orders reaching an unstaffed shop. Cash on delivery is then available immediately.
Stripe also processes Visa/Mastercard credit and debit cards through hosted Checkout.
STRIPE_SECRET_KEY + STRIPE_WEBHOOK_SECRET: create webhook /api/webhooks/stripe for checkout.session.completed, checkout.session.async_payment_succeeded, charge.refunded and charge.dispute.created.
PAYPAL_CLIENT_ID + PAYPAL_CLIENT_SECRET + PAYPAL_WEBHOOK_ID; PAYPAL_ENV=sandbox or live. Optionally PAYPAL_MERCHANT_ID to validate the receiving merchant. Webhook /api/webhooks/paypal: CHECKOUT.ORDER.APPROVED, PAYMENT.CAPTURE.COMPLETED, PAYMENT.CAPTURE.REFUNDED, PAYMENT.CAPTURE.REVERSED.
Use sandbox/test credentials first. Merchant onboarding, provider account approval and live acceptance are external prerequisites. Payment options remain unavailable until configured; no simulated success path exists.
Hamburg delivery fees currently require a restaurant quote before online payment. Once a payment attempt starts, its amount is locked. Refunds/disputes are handled in the provider's dashboard; verified reversal notifications mark the payment for restaurant review. No automatic refund UI is offered.
Verify a real sandbox transaction for each provider before live sales. Automated tests use mocked provider responses and do not prove a merchant account is connected.

EMAIL
Optional RESEND_API_KEY + verified EMAIL_FROM enable password-reset email. Without them, the form explicitly directs customers to the restaurant; it does not claim an email was sent. Admin can create a one-time recovery/invitation link to share privately with a verified customer. Password hashes are never returned by customer APIs.

OPERATIONS
Orders are persisted in D1 and appear in the restaurant desk; the authenticated desk receives order changes through a bounded long poll with a one-second database check. It reconnects after transient failures and rechecks staff authorization during the connection. Keep the desk open to monitor new orders. External SMS/push notifications are not configured.
All order totals are computed server-side. Client prices are checked for changes. A request key prevents accidental duplicate submissions. Guest tracking uses a random private capability token, stored only as a hash in the database.
Staff access is checked server-side. Staff can add/edit/hide products, upload JPEG/PNG/WebP, view/edit/disable/delete customer accounts, generate reset links and manage order status. Customer account deletion retains existing order records.
Complete the legal operator identity, service address, retention terms and restaurant-confirmed allergen data before public sales launch.

MERCHANDISING AND TAX
Admin > Offers / Settings: four button styles, four gallery layouts, four-language special offer, featured products, dated fixed/percentage coupons, minimum spend, usage limits, customer restrictions and product restrictions. Deactivate a coupon to remove it from use; existing orders retain their discount snapshot. Cancelling an unpaid order releases its coupon reservation.
Products support up to five images and primary-image selection; six confidently identified catalogue dishes have three original gallery views, available at 800/1600/2400 pixels. The 120 originals are preserved under assets/originals, outside Git.
Delivery is limited to Hamburg. City and official postcode screening do not prove an individual address is in the delivery area; staff must verify the street/address when confirming the quote. Postal data attribution: Freie und Hansestadt Hamburg, Landesbetrieb Geoinformation und Vermessung, DL-DE-BY 2.0. Default delivery mode is restaurant quote, pending the owner's final fee formula. Legacy A/B prices are an explicit optional setting, not a new assumption.
Tax mode now defaults to provisional no_vat, as requested on 2026-10-11. This charges no VAT and does not assert a legally confirmed §19 exemption. Admin can later choose unset, regular taxation or the confirmed §19 small-business exemption. Prices are gross; regular taxation uses each product's configured 7%/19% rate, applies discounts before VAT, and allocates ancillary delivery by discounted item value. Tax regime/rates/discount shares are snapshotted per order. Changing shop settings does not rewrite existing orders.
Reports cover payment dates in Europe/Berlin, show gross receipts and output VAT, identify unknown tax treatment or reversed payments, and export CSV. This is not a calculation of tax ultimately payable: input VAT, other costs, accounting methods and tax adjustments are outside the store.
Print from a private order page to save an order receipt as PDF. A receipt is not represented as a legally complete VAT invoice; legal operator identity and tax details remain missing. See docs/TAX-SOURCES.json for official sources.

Admin > Offers / Settings > Operations & communication
- Weekly opening/start, same-day order cutoff, delivery start/end, and individual date exceptions; Europe/Berlin. Default work starts 09:00, same-day cutoff 13:00, delivery 14:00–21:00, Thursday–Sunday. These are editable defaults. Closed hours still accept prepaid preorders. At 02:00 on a service day the first selectable slot is 14:00 that same day; after cutoff the next service day is offered. A five-hour preparation lead is enforced server-side, with half-hour choices and a displayed approximate 5–6-hour lead. Manual shop pause stops all new orders. A stale unpaid online order can select a fresh delivery slot before payment.
- Independent cash/Stripe/PayPal/Revolut/SumUp switches. Enabled but unconfigured online methods report an explicit error and never create a paid order. Cards use hosted provider pages. Credentials can be entered in the admin panel and are encrypted with an AES-GCM key derived from AUTH_SECRET; reads return only presence/status, never key values. Keep AUTH_SECRET backed up and stable; changing it requires controlled re-encryption of stored secrets/outbox payloads.
- The Stripe secret key and webhook signing secret, PayPal client ID/secret + webhook ID (merchant ID recommended), Revolut merchant secret key + webhook signing secret, and SumUp API key + merchant code must belong to the store. PayPal/Revolut default to sandbox until the admin selects live. Credential presence is not proof that the merchant has been approved. Complete a provider sandbox and then an authorized live smoke test before opening payments to real customers.
- Configure callback URLs on the public origin: /api/webhooks/stripe, /api/webhooks/paypal, /api/webhooks/revolut, /api/webhooks/sumup. SumUp checkout creation supplies its backend return_url automatically. Localhost cannot receive public provider callbacks without a test tunnel; none was created here. Provider state, currency, amount and order/attempt identity are verified server-side. Stripe/PayPal/Revolut signatures are checked; SumUp notifications trigger an authenticated API lookup and cannot directly mark payment paid. Hosted checkout creation is protected against duplicate requests; an ambiguous interrupted Revolut/SumUp create requires lookup/review rather than blind retry.
